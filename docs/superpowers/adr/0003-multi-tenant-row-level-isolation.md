# ADR-0003: 多租户行级隔离（暂不上库级隔离）

## 状态
2026-09-18 已决策

## 背景
系统需同时支持**私有部署**（单租户）和 **SaaS 多租户**（多公司共享实例）。
需要决定数据隔离粒度。

## 决策
**起步行级隔离**（共享 Schema，业务表加 `tenant_id` 列）：
- 每张业务表必含 `tenant_id BIGINT NOT NULL`
- MyBatis 拦截器自动注入 `WHERE tenant_id = ?`
- 缓存/MQ/文件路径必须携带 `tenant_id`
- 私有部署模式关闭租户拦截，固定 `tenant_id=0`

**暂不**做库级隔离（动态数据源），理由见下。

## 备选方案

| 方案 | 优点 | 缺点 | 决策 |
|---|---|---|---|
| **库级隔离**（每租户独立 DB） | 物理隔离最强；独立备份/恢复 | 动态数据源复杂、运维成本高、跨租户统计困难 | ❌ 暂不 |
| **Schema 隔离** | 中等隔离 | MySQL Schema ≠ PG Schema；运维工具兼容性差 | ❌ |
| **行级隔离（✅ 选中）** | 简单、跨租户聚合易实现、运维统一 | 需严格防漏；备份粒度粗 | ✅ |
| **不分租户** | 最简 | SaaS 不可行 | ❌ |

## 后果

### 优点
- 实现简单：一个拦截器搞定
- 跨租户统计 / BI 数仓同步容易
- 运维统一一套库，备份恢复简单

### 缺点
- SQL 必须严格走 MyBatis 拦截器，否则漏 `tenant_id` 会跨租户泄露
- 单租户数据量爆炸会影响其他租户（需监控告警）
- 备份粒度粗（要么全库备份，要么逐表逻辑备份）

### 漏拦截场景（必须 `@IgnoreTenant` 显式标注）
1. 字典查询 `sys_dict_*`（全局共享）
2. 跨租户统计报表（BI 模块）
3. 超级管理员查询
4. 平台运营类操作（套餐列表）

### 升级路径
当满足任一条件时，升级到库级隔离：
- 单租户数据量 > 1TB
- 单租户对性能要求显著高于其他
- 大客户有独立合规要求

## 强制约束（Code Review 红线）
- ❌ 任何 `SELECT/INSERT/UPDATE/DELETE` 必须经 MyBatis Mapper 接口，**禁止** JDBC 直连
- ❌ 任何 `Redis` key 必须包含 `tenant_id`
- ❌ 任何 `RocketMQ` 消息 payload 必须包含 `tenant_id`
- ❌ 任何文件路径必须 `tenant_id/{biz}/...`
- ✅ 租户解析从 JWT/Header/子域名三处兜底
