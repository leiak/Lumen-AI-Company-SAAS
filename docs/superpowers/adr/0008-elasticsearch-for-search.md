# ADR-0008: 搜索引擎 Elasticsearch 引入必要性

## 状态
2026-09-18 已决策

## 背景
HR、合同、客户、库存等模块涉及复杂检索：
- 员工姓名/手机/邮箱模糊搜
- 合同标题/内容/附件全文搜
- 客户行业/地区/跟进记录多维过滤
- 库存 SKU/批次/库位

MySQL LIKE 在数据量 > 100 万行时性能急剧下降。需要决定是否引入 ES。

## 决策
**引入 ES 8.x**，但**仅用于检索场景**，**不**作为主存储。

## 引入时机的判断

| 数据量 | 检索需求 | 决策 |
|---|---|---|
| < 10 万行 | 模糊搜、组合过滤 | **MySQL** + 索引足够 |
| 10-100 万行 | 简单全文搜 | **MySQL** + FULLTEXT 索引（中文用 ngram parser） |
| > 100 万行 | 复杂全文+高亮+聚合 | **ES** |
| 任意 | 跨模块聚合分析 | **BI 数仓（Doris）** |

## 哪些模块用 ES

| 模块 | 用 ES 检索 | 备注 |
|---|---|---|
| HR（员工） | ✅ 姓名/手机/邮箱 | 员工 < 1 万，可暂不用 |
| 合同 | ✅ 标题/条款/附件 | 长期积累后必须 |
| CRM（客户/商机） | ✅ 名称/行业/备注 | 必用 |
| 库存 | ✅ SKU/批次/库位 | 必用 |
| 财务 | ❌ 按单号/日期检索 MySQL 足够 | |
| 资产 | ❌ 数量小 | |
| 采购 | ✅ 采购单/供应商名 | |
| 销售 | ✅ 订单/客户 | |
| 知识库 | ✅ 全文搜（核心） | |

## 同步策略

```
MySQL (主存储)  ──binlog──→  Canal  ──→  Kafka  ──→  ES (检索)
                                          ↓
                                       Doris (BI)
```

- **写**：业务写 MySQL，binlog 由 Canal 订阅
- **同步**：Canal → Kafka → ES Bulk API
- **读**：业务读 ES（API 层封装）
- **兜底**：每晚全量重建索引任务

## 集群规模

| 规模 | 数据量 | 配置 |
|---|---|---|
| MVP | < 50GB | 3 节点（4C8G） |
| 中型 | 50-500GB | 5 节点（8C16G） |
| 大型 | > 500GB | 独立 ES 集群 + 冷热分层 |

## 后果

### 优点
- 全文检索 + 高亮 + 聚合一站式
- 中文分词成熟（IK Analyzer）
- 与 ELK 共用技术栈

### 缺点
- 运维成本增加（集群 + 同步链路）
- 数据双写一致性需处理（最终一致）

### 风险与缓解
- **风险**：Canal 同步延迟
- **缓解**：监控同步延迟 > 1min 告警 + 业务读走 DB（兜底）
- **风险**：ES 集群脑裂
- **缓解**：至少 3 节点 + `discovery.zen.minimum_master_nodes=2`
