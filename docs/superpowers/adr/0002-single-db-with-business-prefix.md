# ADR-0002: 数据库单库起步 + 业务前缀命名

## 状态
2026-09-18 已决策（用户拍板）

## 背景
17 个业务模块 + 6 个基础服务共用一套数据存储。需要决定：
- 起步阶段是否分库？
- 表命名规则如何？

## 决策
1. **起步单库**：所有服务共用 `lumen_db`（MySQL 8.0），BI 数仓独立 `lumen_bi_db`
2. **表前缀严格按业务域**：`{业务域}_{实体名}`，如 `hr_employee`、`fin_voucher`

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **多库（按业务垂直拆）** | 故障隔离、独立扩展 | 跨库事务、跨库 join 麻烦、初期成本高 |
| **单库（无前缀）** | 简单 | 业务边界模糊、后期分库要重命名 |
| **单库 + Schema 隔离** | 介于两者之间 | MySQL Schema ≠ PG Schema，使用复杂 |
| **单库 + 业务前缀（✅ 选中）** | 简单 + 边界清晰 + 零迁移成本分库 | 仅靠前缀强约束（Code Review 保障） |

## 后果

### 优点
- 初期开发快：跨业务查询简单、本地事务一致
- 未来分库零成本：仅 DDL 导出到不同 instance，表名不变
- BI 库独立：分析查询不拖垮业务库

### 缺点
- 业务表都在一起，DDL 变更需协调（依赖 Flyway 版本化解决）
- 单库性能上限：约 5000 张表；3000 人规模数据量 < 10GB，远未触及

### 风险与缓解
- **风险**：团队不自觉命名（混用 `employee` 与 `hr_employee`）
- **缓解**：Checkstyle 自定义规则 + Code Review 强制 + `db/migration` 命名规范文档

### 分库触发条件
任一条件满足时启动分库：
- 单表数据 > 1000 万行
- 业务库 CPU > 70% 持续 1 周
- 跨业务 join 影响核心接口性能
